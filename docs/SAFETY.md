# Safety model and current limitations

This repository is a **local Go starter**, not a production autonomous agent or ready-to-run exchange bot.

- The interactive trader remains paper-only. `/start_trading` refuses live/autonomous trading and no signal loop is connected to Bitunix orders.
- `internal/bitunix` contains a signed REST client, public trading-pair metadata lookup, order-unit conversion, selected account/position/history/order/TP-SL methods, and a low-level WebSocket transport for public subscriptions and signed private login/subscriptions. The WebSocket transport is not connected to the trader and does not reconnect or reconcile state. REST writes are blocked by default. A REST writer can only be constructed when both the exact `BITUNIX_LIVE_TRADING=I_ACKNOWLEDGE_REAL_TRADING` environment opt-in and the same explicit call-site acknowledgement are supplied. That gate is not an approval UI and is not a substitute for review.
- Client writes were tested against local `httptest` mocks. The only live Bitunix integration test was a public `trading_pairs` read. No private request has been authenticated against a user account, and no live order was submitted. `cmd/bitunix-check` performs only a signed account read when credentials are configured locally.
- Not implemented/wired: autonomous strategy execution, exchange WebSocket reconciliation, partial-fill recovery, exchange-side protection verification loop, liquidation guard, portfolio risk limits, live PnL/report loop, or integration between trader commands and the signed client. A deterministic paper-only `internal/trader.UpdateProtection` calculation now has tests for long/short initial stops, breakeven, trailing, monotonic stop updates, and stop-hit detection. It does not place/modify Bitunix TP/SL orders or consume live position/mark-price feeds.
- The paper calculation interprets `LiqSLDistancePct` as the percentage of the entry-to-liquidation *price gap measured away from liquidation* (50% gives the midpoint). It models ROI as price return × leverage, excluding fees/funding, and uses the tighter of the ROI-lock and price-distance trailing stops. This is an explicit testable provisional interpretation, not confirmation that it matches the user's intended “50% ROI from liquidation” rule. Do not enable it for live trading without confirming the exact rule and price/fee semantics.
- AI support is an OpenAI-compatible HTTP adapter (`GET /models`, `POST /chat/completions`). Listed models may not support chat completions; `/check_ai` tests the selected model. Provider network access depends on local environment access.
- No arbitrary terminal/device access, general filesystem tools, executable MCP/plugins/skills, child-agent spawning, self-patching, or automatic source edits. `/check_system` executes only `go test ./...` and `go vet ./...`.
- `AUTO_ACCEPT_EDITS=true` does not enable edits. No file-editing facility exists. Never grant broad self-modification or unrestricted shell access to a model with exchange credentials.

## Before live orders

Use Bitunix demo trading first. Verify authentication/signature canonicalization, symbol metadata, contract quantity conversion, fee tier, leverage limits, mode semantics, tick/step precision, order acceptance, fills, TP/SL acceptance, and websocket/reconciliation behavior. Enforce max notional, max leverage, max daily loss, symbol allowlists, stale-price checks, idempotent client order IDs, rate limits, independent risk checks, and an out-of-band kill switch. Confirm an exchange-side protective stop exists before treating a position as protected. Reconcile after timeouts because an order may have executed even if the client timed out. Store secrets outside source control and rotate any exposed key.

The user's stop-distance rule (“about 50% ROI from liquidation”) still needs a precise contract: leveraged ROI on margin vs. price movement vs. fraction of entry-to-liquidation price distance; direction-specific formulas; fees/funding; maintenance-margin tiers; and mark-vs-last trigger rules. Do not infer this from prose. Cross-margin liquidation can depend on the rest of the account; a computed estimate is not a guarantee.
